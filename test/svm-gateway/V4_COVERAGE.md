# V4 to V5 regression coverage

The baseline is the deleted suites at PR #1562's base
`0d776a08ff7a79387af3732818f5e23b4bcc473c`. The mapping distinguishes shared behavioral guarantees from retired
interfaces. This is test coverage, not production route enablement or a claim about maximum transaction throughput.

Test names below are in [V5Source](../svm/SvmSpoke.V5Source.ts), [V5Fill](../svm/SvmSpoke.V5Fill.ts),
[RealGateway](RealGateway.ts), [V5Codecs](../svm/SvmSpoke.V5Codecs.ts), and
[retirement compatibility](../svm/SvmSpoke.SlowFillRetirement.ts).

The **Execution lane** column distinguishes automated PR coverage from explicitly run integration tests:

- **CI**: the ordinary SVM check runs `test/svm/**/*.ts` via `anchor test --skip-build`, including V5Source,
  V5Fill, V5Codecs and retirement compatibility. Source/fill execution uses the mock Gateway.
- **Manual**: RealGateway's automated tests run locally via `yarn test-svm-gateway`; the PR workflow does not run
  this lane. Its passing results are local validation evidence.
- **Mixed**: the row names both lanes; the cell identifies which guarantees each covers.

See [the PR workflow](../../.github/workflows/pr.yml) and [Anchor test command](../../Anchor.toml).
The workflow also runs `yarn test-svm-gateway-vectors`, which checks hash vectors without executing the real
Gateway. Guarantees whose replacements run only in RealGateway therefore lost automated PR regression coverage
when the V4 suites were removed, despite retaining executable V5 tests. A green ordinary SVM or vector check
alone does not validate those guarantees.

## Funding and account boundaries

CPI guard is enabled on the user's Token-2022 funding account, with realloc/enable and delegate approval issued as
owner-signed top-level token instructions. It stays enabled throughout execution. The Gateway vault has its own PDA
owner and no CPI guard; the Gateway may approve the Spoke adapter against that vault. The tests reject owner-funded
CPI despite the owner's signature, then prove exact one-shot `StepDelegateTransferFrom` allowance consumption.
Missing/insufficient approvals and downstream failure preserve tokens, allowance, fill status and payer rent.

Native SOL is wrapped with a System Program lamport transfer and `SyncNative`, then funded through Gateway and
consumed by the source adapter. Both existing and newly created wrapped accounts close after the deposit. Tests
check the native mint/event, exact Spoke-vault token and lamport increases, unchanged Gateway-vault lamports, and
payer receipt balances including transaction fees and refunds for closed accounts. Buffer setup transactions are
outside that execution receipt; no token is minted for these cases.

Vault and recipient ATA creation is explicit through the retained `create_token_accounts` instruction. Missing
accounts fail without funding movement or fill-payer debit; provisioning and execution may share one transaction.
The two-fill example uses Gateway parameter buffers, a versioned transaction, an ALT, and a 1,400,000-CU budget.
It establishes that this concrete transaction fits, not a universal maximum number of fills. The old test also
only exercised two fills with an ALT and did not measure a maximum.

This is a composability and atomic-rollback regression. The current V5 relayer submits each order leg separately:
[Jussi prices one path as one Gateway transaction](https://github.com/across-protocol/jussi/blob/305e76ba3be996687f7329f362a48293c84e4dc9/docs/relayer-integration.md#L43),
and [Madrid requires one declared Across fill-JIT slot](https://github.com/across-protocol/relayer-madrid/blob/2356933a6eea6e53f2892dcc107d0c36fbee794b/src/v5-relayer/invariants/Across.ts#L105).
Both fills here share a committed destination step; buffering does not combine independent commitments.
A maximum-fill benchmark is deferred until a concrete relayer batching design establishes the execution shape.

The local R10 run measured 441 bytes / 105,999 CU for one fill and 448 bytes / 212,753 CU for two fills. The tests
enforce the 1,232-byte transaction limit and the configured CU budget; the measured CU values are observations,
not thresholds or throughput guarantees.

Run `yarn test-svm-gateway` for the pinned real-program cases. The ordinary SVM lane runs the mock-Gateway
V5Source/V5Fill/retirement cases. See [the lane guide](README.md) for pins, toolchains, and route-enablement limits.
